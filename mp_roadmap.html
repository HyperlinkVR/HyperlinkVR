Phase A: the forwarding node

  1. Node server [M]. A WebSocket server that:
    • assigns peer IDs and join order, and elects the oldest peer as host
    • forwards frames to one peer, everyone else, or the host
    • notices peers leaving when their socket closes or goes quiet, and cleans up empty rooms
    • uses a versioned wire protocol
  2. WebSocketNetworkEngine carrier [S]. It reports capabilities.unreliable = false, and a dropped connection closes the room with connection-lost (for v1, rejoining just means joining as a new peer).
  3. Service mode [S]. A service_multiplayer setting, a descriptor fetch, a ServiceNetworkEngine that picks the right carrier, and "service" added to the devtools mode.
  4. Extension VR host provides a network engine [S]. Presence then works in the extension too, not just play.
  5. Identity rules [M, can wait until before public testing]. A signed identity handshake, so the node can reject guests and duplicate accounts.

Milestone: presence between real machines and browsers.

Phase B: groundwork, all still singleplayer

  1. Players identified by peer ID [M]. Player.id, target_player in messages, the spawn event carries the ID, the engine's player registry is keyed by ID, and minigolf is re-keyed.
  2. Per-world multiplayer mode [S]. solo / presence / shared in the meta tag, with presence as the default. Solo worlds don't join a room.
  3. Command bus [L]. Every SDK action handler (objects, HUD, VFX, world environment, animations, seeks, monitors, triggers) stops caring whether a command came from the page or the network. It accepts IDs minted by the host, and keeps a compacted log of commands for late joiners.
  4. Session clock sync [S]. So tweens and animations can start at the same moment everywhere.

Phase C: shared mode

  1. Roles [S]. The engine knows if it's host. In shared worlds, clients hand world-level authority (world monitors) to the host.
  2. Command replication [M]. The host broadcasts every command it applies on a reliable channel, and clients apply them.
  3. Client page lifecycle [S]. In shared worlds, client pages never get READY, and the host's "loading finished" is replicated to everyone.
  4. Late join [M]. A newcomer gets the command log replayed, and holds a loading screen until it's caught up.
  5. Report routing [M]. Client engines send reports to the host's page with player attached. Player-targeted actions (teleport, send to world, player monitors) go to that player's engine.
  6. Per-player HUD and effects [S]. Using the scope the HUD already has.
  7. SDK [S]. e.player, players.on_spawn fires for remote players on the host, players.list() and on_leave, and .create() throws on clients.
  8. Host leaves [S]. For v1, the instance simply ends.
  9. Games [S]. Port clubhouse, or a button and score world, to shared.

Milestone: button, score and HUD games are multiplayer.

Phase D: physics

  1. ObjectPhysics honours authority [M]. A body simulated by another engine becomes kinematic and follows the stream.
  2. Host physics streaming [M]. The host streams the pose and velocity of every dynamic body that's moving. It reuses the pose buffer, and stops sending once a body comes to rest.
  3. Grab handoff [L]. A grab claims the object through the host (optimistically, with the host settling conflicts). The holder streams it, and letting go hands it back to the host with its velocity. This is the part that needs the most feel-tuning.
  4. Held objects run their own triggers [M]. Triggers and reports for a held object run on the holder's engine. Other engines replay the visuals only, with reports suppressed.
  5. Pinned ownership [S]. set_ownership(player), needed for minigolf balls.
  6. Remote avatar colliders [S]. So players can push things, and raycasts can hit them.
  7. Games [M]. Minigolf, basketball, defendthecore.

Milestone: physics games are multiplayer. At this point it's "fully working".

Phase E: optional, after that

  1. The local escape hatch: hyperlinkvr.local(), me.create(), message channels
  2. net.state and host migration
  3. Voice chat (its own project)
  4. Presence polish: syncing facial expressions, an interpolation delay that adapts to conditions, binary encoding
  5. Robustness: reconnects, node rate limits and room caps, invites and instance selection (Discord join button), a peer list in the watch UI

Phases A and B don't depend on each other, so you can do them in either order or interleave them. C needs both, and D needs C.
