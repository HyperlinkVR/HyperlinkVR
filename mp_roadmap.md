## Phase B: groundwork, all still singleplayer

6. [x] **Players identified by peer ID [M].** `Player.id`, `target_player` in messages, the spawn event carries the ID, the engine's player registry is keyed by ID, and minigolf is re-keyed (but don't forget singleplayer and reconnects!). Perhaps could use a stable ID, either a UUID stored in their static record, or a hash of the pub key (but keep in mind it may change if a new keypair is generated) although why not just use the username as the peer ID since it is meant to be stable currently. Keeping in mind the identity operator could change any of those fields arbitrarily
7. [x] **Per-world multiplayer mode [S].** `solo` / `shared`, **derived from `max_players` in `hvr-world.json` — no separate mode field** (a second source of truth could contradict the first). `max_players === 1` → solo; `> 1` → shared. The source must be readable *without executing the world*, because the mode gates whether a client even loads the world page — so it lives in the sidecar metadata, never an in-page `<meta>` tag (that'd be circular). Fallback: `mode = solo if (no resolvable metadata) or (max_players === 1) else shared` — note this is *not* the schema's `default(32)`; a parsed-but-omitted field means shared, but unresolvable metadata falls back to solo (never strand someone in shared when the world didn't even resolve). Solo worlds don't join a room. **No `presence` mode** — avatar sync is on in every non-solo world regardless, so `presence` was never a real distinction: for a stateless world it's indistinguishable from `shared`, and for a stateful one it just looks broken (you'd see someone grab a ball and it wouldn't move on your copy). The one real thing under it — a world with no shared mutable state running each client autonomously instead of through the host (no host load, no SPOF, instant local interaction) — survives only as a possible *internal* engine optimisation keyed off a declared-stateless flag, invisible to authors and players.
8. [x] **Command bus [M].** Every SDK action handler (objects, HUD, VFX, world environment, animations, seeks, monitors, triggers) stops caring whether a command came from the page or the network. It accepts IDs minted by the host, and exposes a hook to broadcast each command it applies (the live delta channel, see #11); no command log or compaction here, since late joiners catch up from a state snapshot rather than a replay (see #13). *(The large foundational item — shared mode and physics depend on it.)*
9. [x] **Session clock sync [S].** So tweens and animations can start at the same moment everywhere. **Done:** a shared session clock (`session_clock.ts`) — host is the authority (offset 0), a client estimates its offset NTP-style over a `clock` channel (`ClockSync`), keeping the lowest-RTT sample. Same `stamp` (host, at broadcast) + `session_to_local` (client, at apply) pattern is wired for **animation play/restart**, **transform tweens** (`tween_started_at` on modify), and **client-forwarded report timestamps** (converted to session time in `MultiplayerSync`) — so all start at the correct *phase*. Also on session time: sound/particle playback (`timed_playback.ts`, #13). Not synced, on purpose: screen-space VFX noise (`time_driven` passes read the canvas clock), which is per-viewer and has nothing to agree on. A dynamic seek runs on the body's owner (Phase D).

## Phase C: shared mode

10. [x] **Roles [S].** The engine knows if it's host (`room.self.id === room.host()`). In shared worlds a client hands world authority to the host (`set_world_authority(false)` in `MultiplayerSync`), so world monitors/triggers run host-only. Per-object authority (who simulates and reports for each body) came with Phase D (#20/#22).
11. [x] **Command replication [M].** The host broadcasts every command it applies on a reliable channel, and clients apply them.
12. [x] **Client page lifecycle [S].** In shared worlds, client pages never get `READY`, and the host's "loading finished" is replicated to everyone.
13. [x] **Late join (snapshot, not replay) [M].** A newcomer *pulls* a snapshot of current world state from the host (clear local → request → hydrate, so nothing races), and holds a loading screen until it's hydrated. Not a command-log replay: replaying timing-dependent commands (a tween that started 10s ago) is the fragility to avoid — a snapshot captures `tween X 40% through, started at session-time T` instead. Assets round-trip via `serialise_assets` (AssetRef → url) on the host and `adopt_assets` on the client. **Done: objects** (with live position/rotation sampled from physics, stored scale preserved), **HUD, VFX, world-env** (bridged out of its React-state provider via `world_env_registry`). **Also done:** SDK animations (definition, playback state and captured relative bases, with the epoch in session time), running tweens (start in session time) and seeks, held objects' grab poses (#23), and a **state journal** (`state_journal.ts`). The journal is the latest state-setting interaction/prefab command per target (`set_*`, lock/unlock), from the page or from shared triggers, replayed to the joiner once its objects mount. That covers state that lives inside the engine (a light's colour, a button's label), which the stored objects don't carry. One-shots (play/stop/restart/fire) aren't journalled, so old sounds and effects don't refire. **Ordering:** commands a client gets before its snapshot are already in it, so they're dropped; commands that arrive while it loads are buffered and applied after the snapshot, in order. Wiping the world on join also clears tweens, seeks and animations left over from the page's brief solo run. **Sounds and particles:** interaction playback (play/pause/stop/restart) is journalled too, in one "playback" slot per target, stamped with the session time it fired (the command bus stamps page commands; trigger commands are already stamped). The audio and particle handlers honour that time (`timed_playback.ts`). A looping track starts at `elapsed % duration`, so a joiner hears it in step. A one-shot that already finished stays silent, and a particle burst that's over isn't refired. A replicated play that arrives a hop late also starts that far in, which fixes the live audio offset. A play that arrives before its sound has loaded is held and applied once it has. **Autoplay:** the host stamps each created object's session time (`object_created_at.ts`), and the snapshot carries it. A sound that autoplayed on creation is picked up as far in as it's been playing, for objects a joiner received in its snapshot only. Live creates still start once loaded, so a short one-shot that loads slowly is still heard. An explicit play/pause/stop (including a joiner's replay of one) supersedes autoplay. This same serialisation feeds `net.state` / host migration (#28).
14. [x] **Report routing [M].** Client engines send reports to the host's page with `player` attached. Player-targeted actions (get position, teleport, send to world, player monitors) go to that player's engine: the host forwards any with a remote `target_id` on the `player-action` channel and relays the reply to its page (`player_actions.ts`); a client only accepts them from the host. The spawn event carries each player's username (remote ones from the room roster), so `get_username()` works for remote players. **World monitors and seeks see every player:** player targets resolve by session id (`player_positions.ts`): the local player from their rig, remote ones from their interpolated pose, whose message now carries the player's origin. So the host's distance and player monitors see clients, "any player" means everyone, and a seek chasing player X chases X on every engine. Before, only the local player resolved, so with real (non-null) player ids even the host's own player stopped matching.
15. [x] **Per-player HUD and effects [S].** Using the scope the HUD already has. Needed one player identity across engines: `useLocalPlayerId()` is the room peer id in a room (the node adopts the account uuid as peer id, so logged-in users are unchanged; guests get a minted one), else the account uuid. HUD resolution, report stamping, the spawn event and button presser ids all use it. The host rewrites the SDK's `null` ("local player") in HUD scope/targets to its own id before replicating. Verified in `mptest`. *Caveat:* a guest's peer id only lasts the connection — rejoining resets their per-player state until reconnect tokens (#31).
16. [x] **SDK [S].** `e.player`, `players.on_spawn` fires for remote players on the host, `players.list()` and `on_leave`, and `.create()` throws on clients. A remote spawn fires when the client announces it has spawned (snapshot hydrated, on the `spawn` channel), not on room join, so worlds don't teleport players or drop objects before the client's world exists. The host's own spawn waits for the room so it carries the peer id. **Player identity:** a player id is never null (peer id in a room, account uuid solo, minted for a solo guest), so `null` only survives as internal wire shorthand for "the local player" (the host rewrites it before replicating; the HUD store treats a stored `null` as local). Having an account is a separate fact: `get_account_id()` / `is_guest()`, carried on the spawn event. SDK: `new Player(id)` requires an id, `players.me()` resolves the local player at spawn, `get_id()` is sync, HUD `player()/players()/for_player()` and `set_ownership()` take a `Player` or id (`null` on `set_ownership` still means unpin), `get_current_player()` is deprecated. **Seats:** occupancy is tracked across engines (`seat_occupancy.ts`). Sitting by input takes the seat optimistically and claims it through the host, which confirms it or answers with the real occupant, and the loser stands back up. A leaver's seats are freed, and joiners get the table in the snapshot. The SDK's `seat.sit(player)` / `seat.stand(player)` take a `Player` or id (not a username, so guests work). They're replicated commands every engine applies in order, seating the target on their own engine, and the page's call bumps any occupant. `report_sit` / `report_stand` now fire (`kind: "seat"`, with `player_id`), from the seated player's engine. Before, the engine had no seat command handler or reports at all.
17. [x] **Host leaves [S].** The node already elects a new host, but the old host's page held all the world logic and state, so the new host has nothing running. For v1 the instance simply ends: `NetSession` treats a `host-changed` event (the host only changes when the host leaves) as `host-left`, and a non-`left` room close as `connection-lost`, leaves the room, and exposes `ended`. `MultiplayerSync` then raises the `session_ended_modal` watch modal: *Stay here* (frozen world) or *Find another world* (watch Home). Doesn't auto-rejoin a dead instance. Real migration is #28.
18. [~] **Games [S/M].** *(No longer a "port" — presence is gone, so every `max_players > 1` world is already shared; clubhouse/minigolf run shared as-is.)* **(b) done:** `apps/website/src/mptest/` — a shared counter, a per-player press count, `players.on_spawn`/`on_leave`, and a `.local()` screen-shake trigger. Verified across two browsers, including a late joiner. **(a) in progress — minigolf:** balls and putters pinned per player, `on_leave` cleanup, and the joiner is now spawned and teleported correctly. Engine fixes this shook out:
- A client's "world ready" waits for every hydrated object to load (`wait_for_all_objects_ready`), and its spawn waits for `synced_with_host`, not a `world_ready` left over from its page running the world solo before the room joined.
- **Switching vr ↔ flat no longer remounts the scene.** `<XR>` wraps both modes, `HapticsProvider` is one provider, and the player origin carries its position across the XROrigin ↔ group swap. Previously clicking in reloaded every object and reset the player, which hid the bugs below.
- `PlayerKinematics`: the player is frozen while the loader is up, a teleport zeroes fall speed and becomes the fall-reset point, and in vr mode with no session the capsule stands on the origin (the camera isn't carried yet, so it was standing the capsule at the wrong x/z and sinking the player through the floor).
- The new-document origin reset fires once per document, not whenever `support`/`setWorldEnv` change.
- **Known, deferred: double build on join.** Before the room joins, a client's page runs the world solo (its commands apply locally while there's no transport), then `CommandSync` wipes that and hydrates the host's snapshot. Correct thanks to the wipe and the `synced_with_host` gate, but it costs a full extra load, briefly shows the solo copy, and if metadata resolves after the world loads, the page briefly acts as solo for real (local spawn and its spawn logic). Fix: in a `shared` world, buffer page commands until the role is known, then apply and broadcast as host or drop as client. Revisit for join-time work or if a join bug traces back here.
19. [ ] **WebTransport [S].** for the unreliable channel (making it a hybrid transport, with WebSocket for reliable. Maybe fallback to WebSocket for unreliable if WebTransport isn't available, but need to be careful that all parties agree, so don't do that yet)

**Triggers & anticheat (resolved).** A trigger splits into a *cosmetic* part (muzzle flash/sound — wants to be instant and local) and an *authoritative* part (damage/ammo/score — must be host). These aren't a mode choice: a client-side trigger is **already sandboxed to cosmetics by construction**, because any command it produces is dropped by the bus (only the host authors shared state). So local triggers need no permission system — the command-bus authority *is* the permission. Authoritative effects run host-side off a report the host is free to reject. **Implemented:** a `local` flag on triggers (`.local()` in the SDK). A shared client runs only `local` triggers, for instant cosmetic reactions to its own actions. The host runs every shared trigger, both for events it speaks for and for the reports clients forward to it, and **replicates each command a shared trigger runs** to every client on the command channel (stamped in session time, so an animation it plays starts in step). Before this, a shared trigger's effect happened on one engine only: the host's, or the client's own when its player caused the event.

Anticheat is broader than triggers and is **cleanly additive later** (the architectural half — host-owned state, non-host writes rejected — is already done). `from` proves *who* sent a report, not that it *happened*, so client-asserted events are forgeable. Trust the host as the instance authority (P2P; a cheating host needs a real server, out of scope) and tier event provenance per interaction: **assert** (trust, cosmetic/low-stakes, what we have) → **validate** (host checks reach/cooldown/re-raycast before acting) → **derive** (host detects the event itself from the synced avatar — this is why remote avatar colliders #25 are the anticheat cornerstone). Don't build a global anticheat or an `set_authority` SDK: keep authority implicit (host for state, owner for physics), concentrate the netcode in **prefabs** (a `button` bakes in local-press + report + host reach-check), and add `set_ownership` (#24) as the one physics override. Pose is the irreducible trusted-ish input (sanity-limit speed/teleport only).

**Milestone: button, score and HUD games are multiplayer.**

## Phase D: physics

20. [x] **`ObjectPhysics` honours authority [M].** A body simulated by another engine becomes kinematic and follows the stream. **Done:** `ObjectPhysics` registers every dynamic body with `ownership.ts` (#22), which turns "who owns it" into the `set_remote_simulator` authority fact; `PhysicsSync` flips non-owned bodies kinematic imperatively each frame (not via the `type` prop — see #22). Not owning a body also stops this engine reporting its physics events. Covers prefabs too (they all go through `ObjectPhysics`). Verified: host-driven bodies follow correctly on clients. **Zones and collisions report once:** a report can name its *subject*, the thing that caused it (`ReportSubject` in `report_outbox`), and the subject decides which engine speaks. An object entering a zone or hitting a static object is reported by the host, even when another peer owns and simulates that object: the host runs the zone against the owner's streamed path, so outcomes like "ball entered hole" are derived by the host, not asserted by the owner. This is the "derive" tier of the anticheat plan: a cheater has to forge a plausible path rather than send one fake event. The local player's own body is still reported by their own engine, the only one with that body until #25. Trigger-volume enter/exit, the basketball hoop's score, and collision reports from non-networked objects all use it. Before, they fired on every engine, and a client's copy was forwarded too. Trade-offs: the owner hears "scored" about 100ms + RTT late (use `.local()` triggers for instant feedback), and a very fast body could skip a thin zone. That isn't multiplayer-specific: Rapier's CCD doesn't cover sensors, so a local dynamic body can tunnel a zone in one step too, and the host's follower moves per physics step (interpolated), not per 30Hz sample. If a world ever loses a goal to it: for `ccd: true` bodies only, the engine running zones sweeps the body's shape from its last to its current position each step and synthesises any enter/exit Rapier missed (deduped against Rapier's own events). It helps solo too. Cosmetic `.local()` triggers still fire everywhere. **Object monitors** (an object's own position, velocity and so on) report from the engine simulating it (`speaks_for_object_state`): the owner of a networked body, otherwise the host. Before, a monitor on a static or animated object reported from every engine, and clients forwarded their copies. *Minor, open:* prefab code that pokes the body imperatively (golf ball strike/at-rest, skootball reset) still runs on non-owners against a kinematic body (harmless so far, since its reports are dropped). Remote avatar bodies (#25) are kept out of zones by their `remote_` prefix, and collisions they cause on non-networked objects are host-reported.
21. [x] **Host physics streaming [M].** **Done:** `PhysicsSync` — a body's owner (host by default, see #22) sends full absolute pose + velocity of awake or held dynamic bodies at 30Hz on an unreliable `physics` channel, stamped in session time, plus a few resends when a body falls asleep. Followers buffer per body (`body_stream`, sampled at `session_now() - 100ms`, no offset estimation needed thanks to #9) and drive the kinematic body, snapping on first sample; velocity is used when taking a body over. Loss-tolerant by construction, so WebTransport (#19) drops in underneath with no change. Verified (host-side, incl. held objects). JSON frames for now; binary encoding is #30.
22. [x] **Grab handoff [L].** A grab claims the object through the host (optimistically, host settles conflicts). The holder streams it; letting go hands it back to the host with its velocity. Needs the most feel-tuning. *(This is the VRChat-style ownership model.)* **Done (verified in mptest):** `ownership.ts` — every dynamic body has one owner (host by default); `Grabbable` refuses a body another peer has claimed, claims on grab (optimistic, so the hand drives it immediately), and lets go if the host's owner broadcast takes it back. The host arbitrates claims, broadcasts owners, briefs joiners with the claim table, and reclaims a leaver's bodies (continuing them with their last streamed velocity). **Deviation:** the grabber keeps the body until it *comes to rest*, then releases it — the whole throw plays out on the thrower's engine, so there's no mid-flight handoff to rewind. `PhysicsSync` is now owner-based (whoever owns streams pose + velocity; frames only accepted from the current owner), and enforces body types imperatively each frame (owned → dynamic, otherwise kinematic follower) rather than via the `RigidBody` `type` prop, which would undo a grab's kinematic hold when a claim lands. Joiners get the claim table only once their `PhysicsSync` says `ready` (it mounts late, so anything sent on `peer-joined` could be lost). Ongoing: feel-tuning.
23. [x] **Held objects run their own triggers [M].** Triggers and reports for a held object run on the holder's engine. Other engines replay visuals only, reports suppressed. **Done (untested):**
    - Dynamic grabbables already got this from #22: the grab claims the body, and an owned body speaks for its own reports and triggers.
    - Grabbable's own reports (grab, release, proximity, trigger) now speak for the local player (`ReportSubject`), so a client's proximity report isn't dropped while the host still owns the body.
    - **Held objects:** a grabbable that *isn't* a dynamic body (no body, or a kinematic one) now takes part in ownership too (`register_grab_target`). It's claimed on grab with the host settling conflicts, streamed by its holder while in hand, followed by everyone else (its kinematic body, or the node the grab moves), and handed back as soon as it's let go. Before, only the holder saw it move.
    - The late-join snapshot includes held objects' grab-node poses, so a joiner sees a dropped one where it was left (#13).
24. [x] **Pinned ownership [S].** `set_ownership(player)`, needed for minigolf balls. **Done (verified in mptest):** `handle.set_ownership(player | id | null)` in the SDK → `HVRSDK_SET_OBJECT_OWNERSHIP` → host pins the body (`assign_body_owner(id, owner, pinned)`), replicated in owner broadcasts and the join table. A pinned body stays with its owner (no hand-back at rest, host ignores its release) and nobody else can claim it; the owner's engine simulates it, so their putter hitting it is instant. Pinning is tracked separately from ownership and sent as an explicit `pin` flag (the host's own spawn can fire before it has a room id, so "owner id is null" can't mean unpin), so a body can be pinned to the host too; `null` unpins. A pin to a peer whose `PhysicsSync` hasn't said `ready` yet is held pending, with the body pinned to the host meanwhile so it simulates and nobody can grab it; it transfers once that peer is ready. Refused from a client page; no-op in solo. A leaver's pinned bodies return to the host (unpinned). `mptest` has a shared ball (#22) and one pinned ball per player. Minigolf pins each player's ball and putter on spawn and destroys them on leave (tested under #18). In shared mode the local `PLAYER_SPAWNED` now waits until the room is joined, so the spawn id is always the peer id (unless the session fails, so the world still starts).
25. [x] **Remote avatar colliders [S].** So players can push things, and raycasts can hit them. **Done (untested):** `RemoteAvatar` gives each remote player kinematic bodies that follow their interpolated pose: a head sphere, a torso hull from the mesh, and hand spheres (parked while untracked or before the first pose). They're named `remote_avatar_*:<peer id>`. They push props this engine simulates (the host for unowned ones, the owner for claimed or pinned ones), and a prop's `players` collision filter applies to them. Raycasts hit them, and player hits now carry `player_id` (remote and local), so "who did I hit" is answerable. By default the character controller ignores them, so players walk through each other. A world can turn on `world_env.physics.player_collisions` (SDK: `WorldEnvBuilder.set_player_collisions(true)`); it's replicated and included in the late-join snapshot. Then players block each other: blocking only, because each player's movement runs on their own engine. **Later:** per-player opt-out (`player.set_collidable(false)` for spectators or dead players), and a player-targeted impulse action for shoves and knockback. Zones still only detect a player's own body on their own engine (the `remote_` prefix keeps these out). **Watch:** a client reaching for a host-simulated ball. Its hand reaches the host about 100ms + RTT/2 late, so the grab claim normally lands first, but a fast reach could nudge the ball on the host before the claim. If it does, add touch-to-claim (touching an unowned body claims it like a grab). **Next for anticheat:** host-derived player zone events and putter hits from these bodies.
26. [ ] **Games [M].** Minigolf, basketball, defendthecore.

**Physics anticheat (later, additive).** Owned/pinned bodies are client-authoritative: a cheating owner could stream any pose (e.g. teleport their ball into the hole). Lockstep dual-simulation with exact resync doesn't work — the host lacks the owner's exact inputs (the putter swing arrives late and interpolated), frame timing differs, and floats aren't bit-identical across machines, so honest players would diverge constantly. Instead, layered, all on top of what exists (the host already receives every owner frame in `PhysicsSync`, and `assign_body_owner(id, null)` already revokes and resyncs everyone to the host's copy):
1. **Plausibility checks on the host's receive path:** no teleports beyond what velocity allows, speed caps, inside world bounds, no tunnelling through static geometry (raycast consecutive positions on the host's world), velocity changes only with a plausible cause nearby (a putter near the ball). Fail → revoke ownership.
2. **Host-derived outcomes:** "ball entered hole" comes from the host running the trigger against the streamed path, never from an owner's report — so a cheater has to forge a physically plausible path, which (1) blocks.
3. **Optional loose shadow sim:** the host also simulates the body and flags only *large* divergence — a sanity bound, not an exact check.
4. **Full server authority (overkill unless competitive):** the owner sends inputs only, the host simulates, the client predicts and reconciles (rollback-style, à la Rocket League).

**Milestone: physics games are multiplayer. At this point it's "fully working".**

## Social track: text chat, DMs & friends

A first-class goal (Rec Room parity), run as a **parallel track** to world-sync (B/C/D) — it depends on the relay + identity, not on the command bus or physics.

- [ ] **In-world text chat [S/M].** A reliable `chat` channel + chat UI (log, input, sender identity). Depends only on presence/relay (done), so it can land early — and doubles as a real-payload test of the relay. Sender via `PeerID` now, stable identity once auth lands.
- [ ] **Identity & profiles [M].** Stable user identity (usernames, IDs, profile) — extends Phase A#5 identity rules. Prerequisite for DM addressing and durable message authorship.
- [ ] **Direct messages [L].** 1:1 (and group) messaging independent of sharing a world. Needs: identity (addressing), **message persistence / inbox** (history + offline delivery — a backend store, not just relay forwarding), and routing to a user wherever they are (the relay network, E#31).
- [ ] **Friends / social graph & presence [M].** Friends list, online status, "join friend's instance" (ties into invites / instance selection, E#30).
- [ ] **Safety controls [M, before public].** Client-side **block / mute** (local, needs no server or central authority) and rate limiting. No reporting pipeline — a decentralised network has no central operator to receive one — and no server-side scanning of E2E channels.
- [ ] **E2E for private channels** — see E#32; encrypt chat/DM channels so relay operators can't read them.
- [ ] **Multiple instances** - more than the 1 main instance for each world to split players and allow private lobbies

**Dependency summary:** in-world chat is near-term (relay only). DMs trail identity + persistence, and reaching anyone in the world trails the relay network (E#31).
