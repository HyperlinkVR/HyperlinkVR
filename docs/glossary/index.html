Glossary

Official terminology for HyperlinkVR. Where two words could mean the same thing, the preferred term is the entry heading. Discouraged or easily confused alternatives are mentioned under Not to be confused with.

In some cases, the meaning of an overlapping term is clear by context. When this isn't the case, be sure to use the exact terminology for clarity.

This glossary only serves to avoid confusion when contributing to or using the HyperlinkVR engine and SDK. It is not a comprehensive list of all terms in the ecosystem, nor the game development industry. You shouldn't mandate people follow this glossary to a tee, people are human and will use language in a way that makes sense to them. The goal is to avoid confusion, not to police language.

Meta​

  • HyperlinkVR - the platform, engine, and ecosystem. In speaking, it may be referred to as "hyperlink" for brevity, but only when the context is clear. The platform is not called "Hyperlink".

  • hyperlink.surf - HyperlinkVR's domain name, hosting the website, official worlds, and this documentation!

  • Engine - the HyperlinkVR runtime, which runs worlds and manages players. Currently only shipped as a browser extension, but may technically be used to refer to any implementation of the runtime. "Engine code" refers to code implemented within engine itself, as opposed to code written by a world creator.

  • SDK - the API for interacting with the engine, using declarative and event driven programming. The SDK "talks to" the engine, but is not the engine itself. Most commonly, the SDK will be injected into the browser's JavaScript globals under hyperlinkvr upon the window/globalThis object when the extension is installed.

  • Entity - a general term for anything the engine cares about. Objects, players, animations, interactions, etc.

  • Dispatch - may be either a verb meaning the act of using the SDK to create or modify some entity (objects, HUD elements, animations, etc), or a noun referring to the data itself. For example, you build "an object dispatch" with EngineObjectDispatchBuilder, then you "dispatch it" to the engine with .create(). Colloquially, the term "spawn" may be used in an object context, but this should be avoided to avoid confusion with the concept of player spawning.

  • Handle - an interface often created within the SDK as a result of a dispatch in order to modify it further. For example, EngineObjectDispatchBuilder creates an object dispatch, which is then dispatched to the engine with .create(), which returns a CreatedEngineObject handle that can be used to modify the object further.

  • Type / Kind - a common field used to discriminate entities and payloads. These may be interchangeable, but typically "type" is preferred. If there is the need to have multiple discriminants, "kind" is used for the broader category, and "type" is used for the specific subtype. In rare cases (such as prefab dispatch), a discriminant may be called "name", but this is discouraged as it implies a human-readable label rather than a machine-readable identifier. These are not hard rules, but general guidance for internal engine code.

Worlds & navigation​

  • World - a place a player can visit, loaded from a URL. This is the primary, player-facing meaning: "which world are you in", "send to world", favourite worlds, etc.
    Not to be confused with: World collision layer and Physics world

  • Game - describes a world that implements a game. More of an informal term, but common nonetheless.
    Not to be confused with: HyperlinkVR itself, which is the engine and its ecosystem. Avoid describing HyperlinkVR as a "game" to avoid confusion. "Platform" or "game engine" (depending on the target audience) are better fits.

  • World environment - the ambient properties of a world: sky, fog, gravity, etc. (WorldEnvBuilder, WorldSkyBuilder, WorldFogBuilder).

  • Send to world - moving a player from the current world to another (players.send_to_world).
    Not to be confused with: teleport, which moves a player within the current world.

  • Marker - a creator-defined convention for tagging points/objects in a world so the SDK can find them (load_markers). Most commonly, these will be represented in 3D modelling software as "empties", but technically any object following the set naming convention (default: marker_*) will be detected as a marker.

Objects & prefabs​

  • Object - the fundamental placeable thing in a world (EngineObject). Other terms below describe kinds or aspects of objects, not separate entities.
    Not to be confused with: JavaScript objects, which are a programming construct and not a HyperlinkVR entity. It may be suitable to refer to JavaScript objects or similar constructs as "dictionaries" to avoid confusion.

  • Custom object - an object built from your own selection of mesh, physics, interactions, etc (CustomObjectBuilder).

  • Prefab - a premade, parameterised object implemented in the engine itself (ButtonPrefab, GolfBallPrefab, TextSignPrefab, ...). A prefab is still an object once created.

  • Standard prefab - a prefab which has no special properties (e.g. a basketball), and thus is simply constructed with StandardPrefabBuilder.

  • Mesh - the 3D model/geometry (e.g. a .glb) attached to an object.

  • Prop - a collision group, not an entity type. Props are the physics enabled objects that can be moved, as opposed to fixed/non-physics objects which sit on the world layer, (and of course players sit on the players layer).
    Not to be confused with: object, which is not a synonym for prop. A prop is an object, but not all objects are props (some are fixed world objects for example).

  • Tag - an arbitrary string label attached to an object at dispatch (add_tag), used to identify or group objects at runtime. Object-targeting interactions such as raycast and trigger volume can filter by tag (include-only, or exclude_tags). Tags can also be used for collision filtering, but note this can be expensive at scale.

Physics​

  • Physics system - the physics configuration attached to an object (PhysicsSystemBuilder).
    Not to be confused with: Physics world, which is the simulation itself, not a configuration on an object, or Physics engine, which is the underlying implementation of the physics simulation.

  • Rapier - the underlying physics engine used by HyperlinkVR. Rapier is a Rust library, compiled to WebAssembly for use in the browser.

  • Rigid body - the physical body of an object: dynamic, fixed, kinematic-position, or kinematic-velocity.

  • Collider - a collision shape (box, sphere, capsule, ...). A collider collection groups several on one body. Note that colliders are not exclusively used for physics, they are also used for volumetric applications, such as trigger volume interactions.

  • Collision - the event of two colliders touching.

  • Physics world - the physics simulation itself (the Rapier world): the single space where bodies, colliders, and forces are stepped each frame. There is one per world. Always say "physics world" in full and never bare "world" to keep it distinct from the world (the place) and the world collision layer.

  • World collision layer - the world collision group: immovable scenery and fixed geometry, as opposed to the props (physics objects) and players groups. "World" here names a collision category within the physics world, not the destination.

  • Collision group - one of players, props, or world; controls which other groups a body collides with (collides_with({ players, props, world })). Note world here is the world collision layer above, not the place.

Interactions​

  • Interaction - a behaviour attached to an object that adds additional functionality, often interfacing with the player or world (add_interaction(...)). Examples: grabbable, raycast, trigger volume, seat, follow-player, light (point/spot/directional), audio (positional/global), particle emitter.
    Not to be confused with: a monitor (which observes, rather than adds behaviour) or a trigger (which wires events to commands).

Monitors​

  • Monitor - attaches to an object or player and reports changes in its state as events. Object monitors: position, rotation, linear velocity, angular velocity. Input monitors: button, axis.

  • Object monitor / player monitor - a monitor bound to an object vs. bound to a player.

Events & reporting​

  • Report (verb) - what a monitor, interaction, or prefab does when something happens to raise an event. Also often found on SDK builders as toggles, e.g. reports_grabs(), report_collisions, report_press.

  • Event - the data unit delivered when something is reported, subscribed to via .on("name", (event) => ...). This includes the wrapper around the event payload itself.

  • Payload - the data an event carries that is specific to the event.

    An object reports an event when something happens and every event carries a payload describing it.

Triggers, bindings & commands​

  • Binding - a routable reference to something in a world (an interaction, animation, prefab, etc.) and the conceptual connection point you address it through. You invoke an entity's commands through its binding, and the events it raises are tied to its binding. Internally a binding is backed by a binding ID, and in the SDK you usually give it a name (.named("my_lift"), or the name in add_interaction("bulb", ...)) as a convenience, which is resolved to that ID at dispatch time (BindingConfig).

  • Command - an action invoked on an interaction, prefab, animation, or VFX effect, with optional arguments.

  • Command API - a set of commands exposed by an interaction, prefab, animation etc which is returned on the handle, allowing it to be invoked from the SDK. You may also see terms such as "interaction API" or "prefab API" which are equivalent to "command API" but more specific.

  • Binding host - an SDK-side object that holds a set of named bindings and exposes them for lookup (BindingHost). Typically, a binding host is also a handle. Binding hosts are used by triggers for automatic routing of events to commands on other objects.

  • Trigger - a low latency consequence handled in-engine. This can be thought of as an "if this then that" rule, in which an event causes a command to be invoked. This allows important or simple events to be quickly routed to a command without the overhead of going through the SDK.
    Not to be confused with: a trigger volume interaction, which is a specific kind of interaction that can report events when a player/object enters or exits a collider volume.

  • Trigger target - the destination end of a trigger: the binding to route to (by name on the same object, or on another object via its binding host), plus the command to invoke and any arguments (TriggerTargetBuilder). A single trigger can fire to several trigger targets.

Animation & tweening​

  • Animation - a named set of tracks played together over a duration, with optional loop and autoplay (AnimationBuilder). Started by autoplay or an animation command.

  • Tween - a simpler interpolation between 2 values over time that may be exposed by some entities. Easing refers to the curve (relating value over time) that the tween takes.

  • Track (keyframe track) - animates one channel of an object over time (KeyframeTrackBuilder). There are two kinds of tracks:

    • Continuous - a track holding a value which can be interpolated between keyframes (e.g. position, rotation, scale, float, color).
    • Discrete - a track holding a value which cannot be interpolated between keyframes (e.g. boolean, string).

  • Keyframe - a single (time_ms, value) point on a track (add_keyframe).

  • Interpolation - how a continuous track blends between keyframes.

  • (Animation) Channel - an animatable property of an object that a track can target. An object exposes a fixed set of channels (depending on its interactions) and attempting to target a non-existent channel will fail.

  • Property path - the dotted address of a channel, e.g. "transform.position" or "interactions.bulb.intensity". This is distinct from the channel itself, as it also resolves within nested interactions. For example, a PointLight interaction exposes an intensity channel, but the property path to it is "interactions.NAME.intensity".

Avatar, player, & identity​

  • Player - a participant in a world. Either their in-world presence, or the user themself. Prefer "user" in the latter case when needing to disambiguate.

  • Avatar - the player's visible body/appearance.

  • Expression - the player's facial state (eyes/mouth).

  • Identity - in an authentication context, this refers to the user's name and host that "owns" their account. A username is given in the format name@host, and may be prefixed with an @ in some UI contexts.

UI surfaces​

  • Watch / watch UI / watch menu - the wrist-mounted menu UI (settings, worlds, etc.).

  • Wrist watch - the 3D object on the player's wrist representing the watch as a whole, in which looking at it will open the watch menu.

  • HUD - heads-up overlay layer, separate from the watch.

VFX​

  • VFX stack - the ordered list of full-screen post-processing effects a world applies (VFXStackBuilder, .apply()). VFX stacks are not additive. Applying a stack replaces the current one, and clear() removes all of them.
    Not to be confused with: the engine's own post-processing (tone mapping, SSAO, shadow passes and other quality/optimisation passes, configured via settings), which creators don't control. The VFX stack layers creator effects on top of that.

  • Effect - a single pass within a VFX stack (e.g. bloom, grayscale, screen-shake). There are two kinds of effects:

    • Declarative - a persistent effect that can be configured after via its commands (set, and enable/disable/toggle). Examples: bloom, grayscale.
    • Impulse - a fire-and-forget effect triggered via the pulse command. Examples: screen-shake.

Platform modes & camera​

  • VR - head mounted virtual reality mode. (The official player-facing term is VR. "XR" is internal only and should not appear in UI or docs.)

  • Flat - the non-VR, flat-screen mode (mouse/keyboard/controller).

  • Spectator view - the window/feed shown to onlookers, or the associated perspective (first person, third person, mixed reality).

  • Spectator camera - the camera object that produces the spectator view when in third person or mixed reality mode. Internally, "spectator camera controller" is also used as an all-encompassing term describing the implementation of the spectator camera, which also includes the first person mode (effectively a head mounted, invisible camera).
